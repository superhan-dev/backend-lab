# v1.1.0 Kafka 연동 + 대용량 트래픽 설계 (100만 트래픽 기준)

## 1) 목표와 범위
- 랭킹 기능 쓰기 경로에 Kafka를 도입해 버스트 트래픽(피크 100만 이벤트 기준)을 흡수하고, Redis 실시간 랭킹 업데이트를 비동기로 처리.
- RDB는 여전히 원천 데이터(진실)이고, Kafka→Consumer→Redis는 실시간 뷰 역할.
- k6로 100만 트래픽 부하 테스트 계획 포함.

## 2) 트래픽 가정 및 용량 기준
- 가정: 피크 100만 이벤트/분(≈16.7k req/s). 평균은 이보다 낮으나, 설계는 피크 기준.
- 이벤트: `(user_id, score, play_at, mode/season_id, policy_type[best|acc])`
- 목표 지표(초안)
  - 쓰기 API p99 < 200ms(동기 RDB+Kafka produce 포함)
  - Kafka end-to-end(프로듀스→컨슘→Redis 반영) p99 < 2s
  - 데이터 손실 0, 중복 처리 대비 idempotent 보장

## 3) 아키텍처 흐름
1) Write API: 요청 검증 → RDB `rankings` insert(단일 트랜잭션) → Kafka produce(동기/acks=all) → 성공 응답.
2) Kafka Consumer(ranking-updater): 메시지 소비 → Redis Sorted Set 업데이트(정책별 ZADD GT 또는 ZINCRBY) → 필요 시 메트릭/로그.
3) 실패/지연 대응: Producer 재시도, Consumer 재시도+DLQ, Redis 장애 시 로그 후 재처리/리빌드 가능(원천은 RDB+Kafka 로그).

## 4) Kafka 토픽/파티션 설계
- 토픽 예시: `rankings.scorelog.v1`
- 키: `user_id` 해시 → 같은 사용자 순서 보장, 균형 위해 충분한 파티션 필요.
- 파티션 수(피크 16.7k rps 가정):
  - 목표 소비 처리량: 컨슈머 1개당 ~1k msg/s 처리 시 최소 17개 파티션 필요.
  - 여유 포함 32~48 파티션 권장(스케일/리밸런스 대비).
- 복제/내구성: `replication.factor=3`, `min.insync.replicas=2`, Producer `acks=all`.
- Producer 설정 권장: `compression=lz4`(또는 zstd), `linger.ms=5~20`, `batch.size` 확대(예: 256KB), `retries`/`enable.idempotence=true`.
- Consumer 그룹: `ranking-updater` (파티션 수만큼 병렬 컨슈머 가능).

## 5) 메시지 스키마(초안)
```json
{
  "event_id": "uuid",
  "user_id": "string|int",
  "score": 123,
  "play_at": "ISO8601",
  "mode": "optional",
  "season_id": "optional",
  "policy_type": "best|acc",
  "metadata": {...}
}
```
- `event_id` 기반 idempotency: RDB `rankings`에 `(event_id UNIQUE)` or `(user_id, play_at, score)` 유니크 키로 중복 삽입 방지.
- 컨슈머도 `event_id` 기준 재처리시 안전.

## 6) 소비/업데이트 로직
- 정책 분기:
  - 최고 점수: `ZADD key GT <score> <userId>`
  - 누적 점수: `ZINCRBY key <delta> <userId>` (delta는 메시지 `score`)
- 키 결정: `ranking:<scope>` (`global`, `daily:YYYY-MM-DD`, `season:<id>`, `mode:<mode>:<date>` 등 기존 규칙 재사용).
- 배치 처리: 컨슈머는 `poll` 단위로 파이프라인/멀티 명령 사용, 가능하면 Lua 스크립트로 원자적/대량 처리.
- 장애 처리:
  - Redis 실패 시: 컨슈머 재시도(백오프) 후 실패 메시지는 DLQ로 옮김. DLQ 재처리 잡 별도 운영.
  - 메시지 역직렬화 실패: 즉시 DLQ.

## 7) RDB ↔ Redis 일관성 전략
- RDB insert 성공을 성공 판정 기준으로 두고, Kafka에 적재된 이벤트는 결국 Redis에 반영된다고 가정(at-least-once).
- Redis가 깨질 경우: 관리용 리빌드 잡으로 RDB/Kafka 로그 기반 다시 적재.
- 읽기 API는 Redis 우선, 필요 시 키 미존재/이상 시 폴백(리빌드 트리거 또는 임시 RDB 쿼리).

## 8) 운영/모니터링 포인트
- Kafka: lag, consumer 오류율, rebalance 빈도, broker I/O, ISR 상태.
- Redis: 명령 실패율, 메모리/eviction, latency, replication lag(사용 시).
- API: p95/p99 latency, 에러율, Kafka produce 실패율.
- DLQ: 적재량 모니터링 및 재처리 배치.

## 9) k6 부하 테스트 계획 (100만 이벤트 시나리오)
- 목표: 1분 내 100만 요청(≈16.7k rps) 또는 현실적인 러닝타임으로 동일 총량 도달. 두 프로파일 중 선택:
  - 프로파일 A(피크 스트레스): 60초 동안 1,000,000 요청 도달.
  - 프로파일 B(완화형): 10분 동안 1,000,000 요청 도달(≈1.67k rps).
- 실행 대상: 랭킹 쓰기 API(`/rankings` 등) — RDB insert + Kafka produce 경로 검증.
- 스크립트 예시(HTTP 상정):
```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  executor: 'constant-arrival-rate',
  duration: '60s',           // 프로파일 A: 60s, B는 600s
  rate: 1000000,             // 총 요청 수
  timeUnit: '60s',           // 60s 동안 1,000,000 → ~16.7k rps
  preAllocatedVUs: 2000,
  maxVUs: 5000,
};

export default function () {
  const payload = JSON.stringify({
    user_id: `u-${__VU}-${__ITER}`,
    score: Math.floor(Math.random() * 1000),
    play_at: new Date().toISOString(),
    policy_type: 'best',
  });
  const res = http.post('https://api.example.com/rankings', payload, {
    headers: { 'Content-Type': 'application/json' },
  });
  check(res, { 'status is 2xx': (r) => r.status >= 200 && r.status < 300 });
  sleep(0.001);
}
```
- 관찰 지표:
  - `http_req_duration` p95/p99, `http_req_failed` 비율
  - 서버 측: DB TPS, Kafka produce latency, broker ingress MB/s, consumer lag, Redis latency
  - 오류 로그: Kafka acks 실패, Redis 타임아웃, RDB deadlock
- 준비 사항:
  - 부하 테스트 전용 스테이지/계정, 오토스케일 파드/인스턴스, Kafka 파티션/브로커 리소스 확보
  - 테스트 결과 수집: k6 summary + Prometheus/Grafana 대시보드
